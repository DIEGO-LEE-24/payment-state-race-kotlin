# payment-state-race-kotlin

확정과 취소가 동시에 들어올 때 한쪽 변경이 사라지는 문제를 Kotlin · Spring Boot · PostgreSQL로 재현하고 고친 작은 예제입니다.

요청은 둘 다 성공으로 끝나는데 데이터는 틀려 있습니다. 그리고 **한 종류의 요청만 보내는 동시성 시험은 이 문제를 잡지 못합니다.**

## 결과

`./gradlew test` (PostgreSQL 16, Testcontainers) 실행 결과입니다.

| 구현 | 보낸 요청 | 유실된 라운드 |
|---|---|---|
| 결함 구현 | 확정 + 확정 | 0 / 40 |
| 결함 구현 | 확정 + 취소 | **40 / 40** |
| 고친 구현 | 확정 + 확정 | 0 / 40 |
| 고친 구현 | 확정 + 취소 | **0 / 40** |

첫 줄이 이 예제의 요점입니다. 결함이 있는 구현도 "확정만 동시에 보내는 시험"은 통과합니다.

## 구조

결제 한 건에 딸린 항목별 상태를 한 컬럼의 문자열로 들고 있습니다(`A=PAID,B=CANCELLED`). 상태를 바꾸려면 읽고, 고치고, 통째로 다시 씁니다.

### 결함 구현 — `VulnerableStateChangeService`

```
확정:  세션 행 잠금(처음 본 시각 기록용) → 읽기 → 고치기 → 쓰기
취소:                                      읽기 → 고치기 → 쓰기
```

확정 경로는 "처음 본 시각"을 한 번만 기록하려고 세션 행을 잠급니다. 상태를 보호하려던 잠금이 아닌데, 부수 효과로 확정끼리는 한 줄로 섭니다. 그래서 확정만 보내면 안전해 보입니다.

취소 경로는 그 잠금을 지나가지 않습니다. 확정과 취소가 겹치면 둘 다 같은 옛 값을 읽고, 나중에 쓴 쪽이 먼저 쓴 쪽의 변경을 덮어씁니다.

### 고친 구현 — `SafeStateChangeService`

```
확정 · 취소:  lockForStateWrite(결제 행 FOR UPDATE) → 읽기 → 고치기 → 쓰기
```

상태를 바꾸는 모든 경로가 같은 문을 먼저 지나갑니다. 경로마다 잠금을 따로 고르지 않습니다.

## 시험이 하는 일

- `LostUpdateTest` — 한 라운드마다 결제 한 건을 만들고 두 요청을 동시에 보낸 뒤 DB의 최종 상태가 기대와 같은지 봅니다. 40라운드를 돌려 틀린 라운드를 셉니다.
- `RaceHarness` — 두 요청이 "읽은 뒤 · 쓰기 전"에서 만나도록 합니다. 한쪽이 잠금에 막혀 오지 못하면 먼저 온 쪽은 200ms만 기다리고 혼자 진행합니다. 그래서 같은 시험이 결함 구현에서는 매번 실패하고, 고친 구현에서는 매번 통과합니다.
- `ContentionTest` — 경합 창을 벌리지 않고 결제 한 건에 요청 64개를 2 · 8 · 16개 스레드로 몰아 보내, 모든 변경이 남는지 확인하고 걸린 시간을 출력합니다.

## 범위와 한계

- 두 요청은 **같은 결제 행에 저장된 서로 다른 항목**을 바꿉니다(A 확정, B 취소). 같은 항목에 확정과 취소를 동시에 보내는 시험이 아닙니다. 항목은 달라도 한 컬럼을 통째로 다시 쓰기 때문에 한쪽 변경이 사라집니다.
- 시험은 HTTP 요청이 아니라 서비스 메서드를 직접 호출합니다. 여기서 "성공"은 두 호출이 예외 없이 끝났다는 뜻입니다.
- 다른 프로젝트에서 겪은 문제를 **독립된 예제로 다시 만든 것**입니다. 그 프로젝트의 코드를 옮긴 것이 아니고, 도메인도 다릅니다. 같은 것은 원인의 모양입니다: 두 경로가 서로 다른 잠금을 타고, 한 컬럼을 읽고-고치고-통째로 쓴다.
- 40 / 40은 시험이 경합 창을 일부러 벌렸기 때문에 나오는 숫자입니다. 실제 서비스에서는 타이밍이 맞을 때만 일어납니다.
- 고친 구현은 결제 한 건의 상태 변경을 한 줄로 세웁니다. 한 결제에 요청이 몰리면 그만큼 기다립니다. `ContentionTest`가 찍는 시간은 로컬 한 대에서 잰 참고값이고, 높은 부하에서의 대기 시간은 재지 않았습니다.
- 항목별 상태를 별도 행으로 나누거나, 버전 컬럼으로 충돌을 감지해 재시도하는 방법도 있습니다. 이 예제는 "모든 경로가 같은 잠금을 탄다"만 다룹니다.

## 실행

JDK 17과 Docker가 필요합니다. 로컬에서는 Testcontainers가 PostgreSQL을 띄우고, GitHub Actions에서는 서비스 컨테이너의 PostgreSQL을 씁니다(`TEST_DB_URL`).

```
./gradlew test
```

## 기술

Kotlin 2.0 · Spring Boot 3.4 · Spring JDBC · PostgreSQL 16 · Testcontainers · JUnit 5 · GitHub Actions
